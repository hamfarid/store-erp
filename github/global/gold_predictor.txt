Gold Price Predictor: complete dual-system
architecture guide
This dual-system financial prediction platform—a FastAPI ML backend paired
with a React/Express frontend—requires solving seven interconnected
infrastructure challenges to reach production readiness. The core problems span
Docker containerization of complex ML dependencies, GPU-aware model routing,
automated retraining pipelines, multilingual news sentiment integration, time-series
data storage, monitoring dashboards, and reliable inter-service communication. What
follows is a battle-tested architecture built on proven fintech MLOps patterns, with
concrete configurations, schemas, and code examples for each layer.
The system predicts prices for five assets (Gold, Bitcoin, Ethereum, EGP/USD, TRY/USD)
using four model types (ARIMA, LSTM, Prophet, Ensemble) across three time horizons
(7d, 30d, 90d)—producing 60 distinct model instances that must be trained,
versioned, monitored, and served reliably.

1. Docker configuration that actually handles Prophet,
PyTorch, and statsmodels together
The single hardest Docker problem here is Prophet. It requires a C++ compiler ( g++ )
and cmdstanpy , which compiles Stan models during installation.

without GPUs, torch.cuda.is_available() returns False and PyTorch falls back to CPU
transparently.

2. GPU auto-detection routes LSTM to GPU while ARIMA
and Prophet stay on CPU
ARIMA (statsmodels) and Prophet are CPU-only libraries—they have no GPU codepath.
Only LSTM (PyTorch) benefits from GPU acceleration. The model manager pattern below
handles this automatically:
class ModelManager:
def __init__(self, model_dir: str = "/app/models"):
self.model_dir = Path(model_dir)
self._models: dict[str, object] = {}
self._load_status: dict[str, str] = {}
self.device = torch.device("cuda" if torch.cuda.is_available() else "cpu")

Memory budget for the full model stack: LSTM models are typically 10-100MB per
asset, ARIMA ~1-5MB, Prophet ~1-10MB, Ensemble configs under 1MB. Total on-disk:
~300MB for all 20 models. Runtime memory is 2-3× that (~600MB-1.5GB per worker).
With 3 Docker replicas running 1 Uvicorn worker each, budget ~1.5-4.5GB total RAM
for the ML service cluster. Running single-worker-per-container avoids PyTorch’s known
issues with Gunicorn --preload fork semantics.
For LSTM time-series models specifically, the performance difference between CPU and
GPU is modest for inference (these are small models, not GPT-scale). A financial LSTM
with 2 layers and 128 hidden units runs inference in <100ms on CPU. GPU matters
primarily for training, where weekly retraining of 5 assets might take 25-150 minutes on
CPU versus 5-15 minutes on GPU.

Each training task follows a strict pipeline: acquire Redis lock → fetch data → validate
→ train candidate → evaluate on holdout → compare with production model →
promote if better → release lock. The training lock uses Redis SET NX EX with a Lua

script for atomic owner-only release,

Redis

preventing concurrent training of the same

model:
class TrainingLock:
def __init__(self, model_type, asset, timeout=3600):
self.redis = redis.Redis(host='redis', port=6379, db=2)
self.lock_key = f"training_lock:{model_type}:{asset}"
self.lock_id = f"{model_type}_{asset}_{time.time()}"
def acquire(self):
return bool(self.redis.set(self.lock_key, self.lock_id, nx=True, ex=self.timeout))
def release(self):
lua = """
if redis.call("get", KEYS[1]) == ARGV[1] then
return redis.call("del", KEYS[1])
else return 0 end"""
return bool(self.redis.eval(lua, 1, self.lock_key, self.lock_id))

Drift detection triggers emergency retrains
The drift detector combines four signals: Population Stability Index (PSI > 0.20 =
critical), Kolmogorov-Smirnov test

Naitive

Acceldata

(p < 0.05), MAPE degradation

(>50% increase from baseline), and directional accuracy (below 50% = worse than
random). When drift is detected, an emergency retrain fires immediately regardless of
schedule.

Ensemble weight optimization
Daily optimization uses inverse-error weighting with exponential forgetting
(λ=0.95, so recent errors matter more). Weekly full optimization uses scipy SLSQP to
directly minimize ensemble MAPE on the last 30 days of predictions. A floor weight of
0.05-0.10 prevents completely excluding any model, and z-score monitoring detects
sudden model failure (z > 2.5 → reduce weight to floor).

Circuit breaker with cached fallback
The Express backend wraps all FastAPI calls in a circuit breaker (using opossum ). When
the ML service is down, the breaker opens after 50% failure rate and returns cached
predictions with a staleness badge. Retry uses exponential backoff with jitter (2s, 4s,
8s base delays + random 0-1s jitter).

Real-time price updates via tRPC subscriptions (SSE)
FastAPI publishes price updates to Redis PubSub channels ( price:gold ,
price:bitcoin , etc.). Express subscribes to these channels and exposes them as tRPC

subscription endpoints using Server-Sent Events. tRPC v11’s tracked() helper handles
reconnection automatically—when a client disconnects and reconnects, it sends the last
known event ID, and the server replays missed events from a Redis buffer.

Claims of >70% directional accuracy on 90-day horizons for volatile assets
should be treated with extreme skepticism—this almost always indicates overfitting,
lookahead bias, or data snooping. The five critical pitfalls to guard against: lookahead
bias (using future data in features—enforce strict temporal train/test splits),
survivorship bias (use point-in-time data), overfitting (ensemble methods and walkforward validation mitigate this), data snooping (document all experiments, use
Bonferroni correction), and narrative bias (LLMs rationalizing predictions post-hoc—
separate prediction from explanation).

Conclusion
The architecture converges on several non-obvious decisions. One Docker image with
CUDA PyTorch serves both GPU and CPU machines—GPU override files handle the
rest. Celery + Redis beats APScheduler for ML training because distributed locking,
task chaining, and failure recovery matter at scale. TimescaleDB as a PostgreSQL
extension avoids a database migration while delivering 20× faster time-series queries
through hypertable partitioning and continuous aggregates. Three dashboard
technologies aren’t redundant—Grafana handles alerting, Streamlit handles
interactive analysis, and React serves end users. The Express backend is inherently a
BFF that proxies to FastAPI via REST; no API gateway needed for two services. And
dynamic news caching based on market hours, volatility, and article velocity
dramatically outperforms any fixed TTL. Together, these choices create a system where
models retrain themselves when drift is detected, news sentiment feeds prediction
features in real time across two languages, and the entire pipeline is observable from
training loss curves to production prediction accuracy.
